Architecture

Web Analyst Agent

A local web app that takes a link and an objective, picks or writes a skill for that kind of analysis, gathers evidence from the site, and returns a report where every finding cites what was observed. Models come from OpenRouter's free tier, with a second chain and a fallback API behind it.

How a request travels

One run crosses six components, and the only two places it leaves your machine are the model providers and the site being analyzed. The numbered markers on the figure match the steps below it.

  1. You submit a link and an objective. index.html posts them to /api/runs. server.py checks the URL shape and lengths, and refuses if two runs are already active.

  2. runs.py creates a run with a random id, starts a thread, and returns the id. The page opens /api/runs/{id}/events, a server-sent event stream that replays the run's log from event 0, so reloading the page or opening a second tab still works.

  3. agent.py builds the first messages: the system prompt, the target, the objective, and a catalog with one line per skill. If you chose a perspective, its lens is placed first and the catalog shrinks to that role's skills. If you picked skills in the form, their full text is placed in this message too, so the model does not spend requests loading them.

  4. Each turn, llm.py sends the messages and the tool schemas to OpenRouter chain 1, then chain 2, then the fallback API. The first success returns text, optional reasoning, and tool calls.

  5. Tool calls go to tools.py. Skill calls read or write skills/. Fetches go through webfetch.py, which validates the URL, follows redirects one hop at a time, and returns a structured summary that is marked as untrusted.

  6. Every step becomes an event. The model's first reply with no tool call is the report. runs.py then saves the events, metadata and report under runs/<id>/.

The agent loop

One pass through the loop is one model request. The loop ends when the model answers without calling a tool, or when the turn cap is reached. A few guards keep weaker free models honest.

Failover in llm.py

Endpoints are tried in order: OpenRouter chain 1, OpenRouter chain 2, then the fallback API. OpenRouter accepts at most three models per request, so the model list is split into two chains of three on the same key. The conversation uses plain OpenAI message format, so a run can change provider halfway through without any translation.

What comes backWhat the client does
200 with text or tool callsReturns it, after removing any leaked think and tool_call markup.
429 with a short Retry-AfterWaits that long (at most 20 seconds), then retries, up to twice.
429 naming a daily quotaSkips the retries and moves on. Any other chain on the same key is skipped too, since it shares the quota.
5xx, timeout, network errorRetries after 2 seconds, then 4, then moves to the next endpoint.
200 with an error body and no choicesTreated like a 5xx or a 4xx, depending on the code inside the body.
400, 401, 403, 404No retry. Moves to the next endpoint at once, since another provider may accept the request.
Every endpoint failedRaises one error that lists each reason without any key. The run ends with that message in the UI.

Where trust changes

Anything a website says, and anything the model writes, is treated as input to be checked. The orange parts of the first figure are the places that matter most.

InputControl
URL from the user or the modelhttp and https only, no embedded credentials. The host is resolved and refused if any address is private, loopback or link-local. Every redirect is re-checked, with at most 5. Bodies stop at 2 MB, requests at 15 seconds, runs at 25 fetches. robots.txt is honored.
Page content going to the modelResults are a structured summary, not raw HTML, and carry a note that the content is data. The system prompt tells the model to report injection attempts and not follow them.
Skills written by the modelThe name must be a lowercase slug of at most 48 characters. Bodies are capped at 20,000 characters. Writes stay inside skills/, overwriting needs an explicit flag, and the old version is archived.
Report shown in the browserEscaped before any markup is added. Only http and https links are rendered. Event text is inserted with textContent.
Requests to the serverLocalhost Host headers only, JSON bodies only, no CORS headers, so other websites cannot start runs from your browser.
API keysKept in .env, which is gitignored. Errors and events never include them.

Known gap: DNS is checked once for validation and the HTTP client resolves the name again when it connects, so DNS rebinding is not fully closed. Run the app somewhere with no route to internal systems if that matters to you.

Skills

A skill is a Markdown playbook, one folder each. The agent never executes anything it writes, so there is no sandbox to build or trust.

Perspectives

The same site needs a different report depending on who asks. A perspective is a small JSON file with a lens (how to frame findings and what to leave out), the skills that fit that role, and example objectives. Five ship: Product Manager, SEO Analyst, Front End Engineer, Back End Engineer and AI Engineer. Adding a sixth means adding one file.

Life cycle

Installed. At startup, any folder in seed_skills/ that is missing from skills/ is copied in. Existing folders are never touched.

Used. The first message carries one line per skill, the name and description. When the model picks one, load_skill returns the full body. If you choose skills in the form (up to 5), their bodies are inlined instead, and you can switch off skill writing for the run.

Created. When nothing fits, the model writes a new skill with save_skill before it starts the analysis.

Improved. Saving over an existing name raises the version and archives the previous text in .history/.

What it cannot see

The tools read server-delivered HTML and headers. They do not run JavaScript, so content drawn by scripts, real load timing, and logged-in pages are out of reach. The skills say this in their pitfalls, and the report is told to state it. The app has no login and keeps runs in one process, so it is built for one person on one machine.
